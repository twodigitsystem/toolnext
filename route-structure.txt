Category-Driven Sidebar Design — Routes & Structure
Great design idea. Below is a full evaluation of the UX, then the colocation-first route structure using Next.js route groups + private folders (_) — everything for a tool lives in its own route folder.

✅ Why this design works
Strength	Why it matters
Persistent sidebar	Users always know where they are — no dead-ends
Category = mental model	Matches how people think ("I need a converter")
Fast discovery	Click category → see all siblings without going home
Keyboard-friendly	Sidebar is a natural tab order for power users
Bookmarkable tools	Direct URL to any tool still works
⚠️ Watch out for
Category must be derived on tool pages — otherwise the sidebar can't highlight the active category. Solution: the tool registry is the source of truth — every tool knows its category, so the sidebar looks it up.

Don't duplicate the sidebar in every layout — put it in a shared group layout so it persists across category → tool navigation.

Mobile: sidebar becomes a slide-over drawer (Sheet) — don't show it inline below md.

🗺️ Recommended Route Structure
This is the best structure for your constraints — colocation + private folders + persistent sidebar.

📌 The key insight
Route	URL	Sidebar shows
(browse)/categories/[category]	/categories/developer	Developer tools
(browse)/tools/json-formatter	/tools/json-formatter	Developer tools (from registry lookup)
The sidebar derives the active category:

On /categories/X → category is X (from params)

On /tools/Y → category is tools.find(t => t.id === Y).category (from registry)

No category in the tool URL. Clean, bookmarkable, and the sidebar still knows.

🆚 Why not /categories/[category]/[tool]?
You could nest tools inside categories, but it breaks colocation:

text
❌  categories/[category]/
    ├── layout.tsx
    ├── page.tsx
    └── [tool]/                       # Dynamic — every tool shares this folder
        ├── page.tsx
        └── _tools/                   # ❌ not colocated — all tools lumped together
            ├── json-formatter/...
            ├── base64/...
            └── regex-tester/...
Concern	Nested [tool]	Static per-tool ✅
Colocation	❌ tools share one [tool]/ folder	✅ each tool own folder
Private folders	❌ _tools/ becomes a dump	✅ _components/ + _lib/ per tool
Type safety	❌ string lookup at runtime	✅ direct imports in page.tsx
Code splitting	❌ harder to isolate	✅ automatic per route
URL can lie	❌ /categories/text/json-formatter → 404 needed	✅ no ambiguity
Verdict: static per-tool routes win for a heterogeneous tool collection.
